# Porting Argus's desktop side to Rust

I decided on 2026-11-11 to port the desktop side of Argus (the qFlipper fork) from C++/Qt to Rust. My order of
priorities is security, then stability, then speed, and everything of ours that can be Rust becomes Rust. What runs
on the Flipper stays C: the firmware (Argus_Firmware) is not part of this port, and neither is any C the device runs.

The port stays GPL-3.0, like qFlipper. Every new crate says `license = "GPL-3.0-only"`.

What talks to the device, by channel:

- **USB serial (CDC-ACM, VID 0483 PID 5740):** the text CLI for the handshake, then protobuf RPC. Everything in
  `protobufsession`, `rpc/`, `utility/`, `toplevel/` (until a flow reboots into DFU), the screen streamer, our capture
  pull, snapshots and app installs.
- **USB DFU (PID DF11):** `dfu/` and `recovery*`: firmware, radio stack, FUS, option bytes. This is the only part that
  can brick a device.
- **Network:** the update directories on Flipper's server (firmware; the app's own self-update is off in every build)
  and region provisioning. The Sarina control API listens on loopback only.

## 3. The order

Protocol and device logic first, with the CLI as the proof surface; the UI last.

1. **Protocol and read-only CLI.** Messages, framing, the serial handshake, request matching, read-only
   operations; `argus-cli info` and `ls`. *Done 2026-11-12 (section 5).*
2. **The rest of the reads.** Stat, storage info, MD5, file read and directory download (with the C++ path checks:
   no `.`/`..`, backslash or NUL in device names), file tree, date/time read. CLI: `stat`, `df`, `md5`, `date`,
   `pull`, and upstream's `backup` (reads `/int` into a tar.gz). A real serial port only when named.
   *Done 2026-11-12, except screen frames (with the screen streamer, phase 3).*
3. **Our subsystems.** Capture pull and pull-all with the allowlist (secrets are never read), the SQLite datastore,
   pcap export, the `.nfc`/`.sub` parsers (argus-tools has them), the Sarina control API server (loopback, token
   always required, same wire format, `docs/SARINA_API.md` stays the contract), the event log. CLI parity with
   `qFlipper-cli chymaera ...`, so Sarina's clients see no change.
4. **Writes, behind a confirmation.** Write, mkdir, rename, remove, restore, app installs, date/time set, reboot.
   Nothing reachable from the Sarina API transmits, flashes or changes the device without my approval in the app.
5. **Firmware update over the updater** (package upload plus `SystemUpdateRequest`), factory reset (`erase`).
6. **DFU and recovery** with nusb: DfuSe parsing first (pure, fuzzed), then option bytes, FUS and radio stack. No
   flashing in tests, and none on my device until I say so.
7. **Update registry and region provisioning** (HTTPS with rustls, SHA-256 checked before anything is used).
8. **The UI** in egui/eframe, window by window. When it covers what the QML does, the C++ goes (no dead code left).

## 4. How the port is proven without a device

No test opens `/dev/ttyACM*` or any real device, and nothing flashes. The proof has four layers:

1. **The schema against the C++ app's.** `tests/nanopb_schema.rs` reads every `*_FIELDLIST` macro in
   `plugins/flipperproto0/messages/*.pb.h` and checks each field (number, type, repeated, oneof) against the
   Rust schema. 144 fields in 67 messages match; the Rust schema is newer (protocol 0.25) and has more, never fewer.
2. **The bytes against the C++ app's encoder.** `tests/nanopb/driver.c` is built from the C++ app's own generated
   `.pb.c` files and nanopb (plain C, no Qt), fills each request exactly as the plugin's request classes do and each
   response as the firmware does, and prints the frames to `tests/fixtures/nanopb_frames.txt`. The Rust requests are
   byte-identical; the responses decode to the same values and re-encode to the same bytes. CI rebuilds the
   fixture from the C code and fails if it changes.
3. **A fake Flipper** (`crates/flipper-fake`): prints the banner and prompt, answers `start_rpc_session`, and
   serves read-only RPC from a scripted device, following the firmware's code (8 entries per list frame, `/` lists
   `any`/`int`/`ext`, non-ASCII names left out, property streams end with an empty frame, errors carry empty
   content). It records every byte the client sends, and it can misbehave on purpose: no prompt, silence, a garbage
   frame, an oversized frame, an error status, a flood of frames for other ids, a wrong response type, a cut-off
   frame. The CLI tests run the real `argus-cli` binary against it over a Unix socket and compare stdout (one JSON
   object), stderr, the exit status and the bytes on the wire, which must equal the C++ encoder's frames.
4. **Property tests and fuzz targets for every decoder.** The frame decoder has proptests (any bytes cut anywhere
   never panic and never buffer past the limit; messages round-trip however the stream is split; junk after valid
   frames does not lose them) and a cargo-fuzz target (`argus-tools/fuzz`, `rpc_frames`). Each new decoder gets the
   same: file listings and reads (phase 2), update manifests and `directory.json` (phase 7), DfuSe files (phase 6),
   tar backups (phase 2).

**The C++ CLI against the same fake.** The C++ app finds a Flipper by USB VID/PID. A test-only hook
(`backend/testhooks.h`) changes that only when `ARGUS_TEST_SERIAL_PORT` names a port: the registry then does not
watch USB at all (a real Flipper plugged in is never seen), uses that port as the one device, does not raise DTR
(a pseudo-terminal has no modem lines) and does not fetch the firmware directory (no network). Unset, nothing
changes. The fake serves a pseudo-terminal (`flipper-fake --pty`), session after session as the C++ app reopens
the port. `argus-tools/crates/flipper-fake/compare-cli.sh` runs `qFlipper-cli backup` and `argus-cli backup`
against it and compares exit codes, the archives' files and bytes, and the requests each sent (decoded by the
fake, ids aside); it refuses a `qFlipper-cli` built without the hook. The Linux build workflow runs it after the
Qt build. Result on 2026-11-12: same files, same bytes, same storage requests in the same order. The C++ app
also probes the device first (protobuf version, `devinfo`, storage info, `/ext/Manifest`, reads and **sets the
clock**) and starts the screen stream and a status screen; the Rust CLI does none of that.

## 5. Status (2026-11-12)

In `argus-tools/` (now a Cargo workspace; `cargo build` there still builds only argus-tools, as the Qt build expects):

- `crates/flipper-rpc`: messages (prost, built from `proto/`; needs `protoc`), framing with a 16 KiB frame limit,
  the handshake, request matching (command ids from 1, 0 kept for broadcasts), read-only operations: protobuf
  version, device info (the `devinfo` property from protocol 0.14, the old request before), list, stat, storage info.
  Transports: a serial port opened only by path (DTR pulsed as the C++ app does) or a Unix socket.
- `crates/flipper-fake`: the fake Flipper (library and `flipper-fake --socket PATH` binary).
- `crates/argus-cli`: `argus-cli (--port DEV | --socket PATH) info | ls PATH | version`. JSON on stdout like
  argus-tools; exit 1 for device or protocol errors, 2 for usage. It never searches for a device.
- Phase 2 (2026-11-12): MD5, file read (stat and read under one id, as the C++ app), date/time, file tree, pull,
  backup; `argus-cli stat|df|md5|date|pull|backup`; the fake's pseudo-terminal mode; the C++ test hook and
  `compare-cli.sh`.
- The C++ fixes above (2026-11-12): `chymaera selftest` 17/17 (six new checks: old and new archives, end blocks, long
  names, device names); `compare-cli.sh` 26/26 over six scenarios.
- Tests: 64 in the new crates (frames, paths, schema, nanopb fixtures, session and reads against the fake with
  every fault, hostile names, the CLI binary over a socket and a pseudo-terminal), all green; argus-tools' own
  tests unchanged; `qFlipper-cli chymaera selftest` 11/11 with the hook built in.

Differences from the C++ app found so far, all on purpose or harmless:

- **A corrupt stream stalls the C++ app.** It appends to its buffer until nanopb manages to decode, so a broken
  frame means waiting forever with a growing buffer. The Rust decoder tells "incomplete" from "invalid" and ends the
  session with an error; frames over 16 KiB are refused from their length prefix.
- **Empty strings.** nanopb sends a set-but-empty pointer string (`path: ""`), prost leaves it out; both decode the
  same. The Rust operations never send an empty path.
- **The C++ device-info flow sets the device's clock** on every connection. `argus-cli info` only reads.
- **`status.pb.c` is dead in the C++ app**: compiled, never used (the old `PB_Status` ping; ping is in `PB_System`).
  Not ported. Upstream's code, so I leave it there until the C++ goes.
- **Strings must be UTF-8 in Rust** (proto3 `string`); a frame with invalid UTF-8 fails to decode with an error,
  where the C++ app passes the bytes on. The firmware leaves non-ASCII names out of listings anyway.
- **Bytes glued to the `start_rpc_session` echo** are kept as RPC data; the C++ app would discard them and time out.
- **Control characters** (including DEL and the C1 range) in anything printed are escaped, so a file name on the
  device cannot drive the terminal.

Found in the C++ app by running it against the fake, and **fixed in both versions** on 2026-11-12 (a bug the
port finds is fixed in the C++ too). `compare-cli.sh` has a case for each, and both apps now agree on all of them:

- **A missing `data` field crashed it.** `storageresponse.cpp`, `guiresponse.cpp` and `statusresponse.cpp`
  dereferenced nanopb's `data` pointer unchecked; a device that leaves an empty `bytes` field out (valid proto3;
  the firmware never does) made the app segfault. Now a missing field is empty. Cases: `omit-empty-data`,
  `frame-without-data`.
- **Screen frames of the wrong length** were drawn anyway: the canvas reads 1024 bytes for the 128x64 screen, so a
  shorter frame read past the end. The streamer now drops any frame that is not exactly 1024 bytes. (The Rust port
  must do the same when it gets the screen streamer, phase 3.)
- **A short or long read went unnoticed.** `StorageReadOperation` now fails when the bytes received differ from the
  stat, which covers backup, directory download, capture pull and snapshots. The backup exits non-zero and leaves
  no archive. Cases: `short-read`, `long-read`.
- **Its backups confused standard tar, and its restore lost files from them.** The writer added a zero block after
  any 512-aligned file (GNU tar stopped there), truncated names over 99 bytes and wrote no end blocks; it now pads
  correctly, refuses long names and ends with two zero blocks. The reader ended at the second zero block anywhere
  in the archive, so an old archive with two 512-aligned files lost everything after the second; it now ends only at
  two zero blocks in a row, so old and new archives both restore whole (`chymaera selftest` checks both).
- **No name checks in backup and directory download, and a delete.** `GetFileTreeOperation` now leaves out (and
  lists as refused) any name that is empty, `.`, `..`, not UTF-8, over 255 bytes, or holds `/`, `\`, NUL or a
  control character, the same rule as the Rust `safe_name`; nothing under such a name is read. The directory
  download refuses an existing local folder instead of deleting it. Case: `hostile`.
- **An empty tree hung backup and directory download** (they waited for a last file that never came); they now go on.

What still differs, on purpose: the C++ app probes the device before a backup (and **sets its clock**) and starts the
screen stream and a status screen; the Rust CLI only reads what the command needs. The C++ restore of an archive and
the Rust backup agree; a restore from Rust waits for writes (phase 4).
