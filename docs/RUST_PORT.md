# Porting Argus's desktop side to Rust

I decided on 2026-11-11 to port the desktop side of Argus (the qFlipper fork) from C++/Qt to Rust. My order of
priorities is security, then stability, then speed, and everything of ours that can be Rust becomes Rust. What runs
on the Flipper stays C: the firmware (Argus_Firmware) is not part of this port, and neither is any C the device runs.

The port stays GPL-3.0, like qFlipper. Every new crate says `license = "GPL-3.0-only"`.

What talks to the device, by channel:

- **USB serial (CDC-ACM, VID 0483 PID 5740):** the text CLI for the handshake, then protobuf RPC. Everything in
  `protobufsession`, `rpc/`, `utility/`, `toplevel/` (until a flow reboots into DFU), the screen streamer, our capture
  pull, snapshots and app installs.
- **USB DFU (PID DF11):** `dfu/` and `recovery*`: firmware, radio stack, FUS, option bytes. This is the only part that
  can brick a device.
- **Network:** the update directories on Flipper's server (firmware; the app's own self-update is off in every build)
  and region provisioning. The Sarina control API listens on loopback only.

## 3. The order

Protocol and device logic first, with the CLI as the proof surface; the UI last.

1. **Protocol and read-only CLI.** Messages, framing, the serial handshake, request matching, read-only
   operations; `argus-cli info` and `ls`. *Done 2026-11-12 (section 5).*
2. **The rest of the reads.** Stat, storage info, MD5, file read and directory download (with the C++ path checks:
   no `.`/`..`, backslash or NUL in device names), file tree, date/time read. CLI: `stat`, `df`, `md5`, `date`,
   `pull`, and upstream's `backup` (reads `/int` into a tar.gz). A real serial port only when named.
   *Done 2026-11-12; screen frames too (`argus-cli screen`).*
3. **Our subsystems.** Capture pull and pull-all with the allowlist (secrets are never read), the SQLite datastore,
   pcap export, the `.nfc`/`.sub` parsers (argus-tools has them), the Sarina control API server (loopback, token
   always required, same wire format, `docs/SARINA_API.md` stays the contract), the event log. CLI parity with
   `qFlipper-cli chymaera ...`, so Sarina's clients see no change.
   *Started 2026-11-12: capture pull and pull-all into the shared datastore (`crates/argus-capture`,
   `argus-cli capture pull PATH | capture pull-all`). Then the control API server, the event log, pcap
   export and `chymaera serve|parse|import|selftest` (`crates/argus-api`, `argus-cli chymaera ...`).*
4. **Writes, behind a confirmation.** Write, mkdir, rename, remove, restore, app installs, date/time set, reboot.
   Nothing reachable from the Sarina API transmits, flashes or changes the device without my approval in the app.
   *Started 2026-11-12: write, mkdir, remove, rename, restore, reboot and the factory reset (`erase`, from phase 5)
   in `flipper_rpc::write` and `flipper_rpc::restore`; `argus-cli mkdir|rm|mv|push|restore|reboot|erase`, each
   doing nothing without `--yes`. App installs and date/time set are still to come.*
5. **Firmware update over the updater** (package upload plus `SystemUpdateRequest`), factory reset (`erase`).
6. **DFU and recovery** with nusb: DfuSe parsing first (pure, fuzzed), then option bytes, FUS and radio stack. No
   flashing in tests, and none on my device until I say so.
7. **Update registry and region provisioning** (HTTPS with rustls, SHA-256 checked before anything is used).
8. **The UI** in egui/eframe, window by window. When it covers what the QML does, the C++ goes (no dead code left).

## 4. How the port is proven without a device

No test opens `/dev/ttyACM*` or any real device, and nothing flashes. The proof has four layers:

1. **The schema against the C++ app's.** `tests/nanopb_schema.rs` reads every `*_FIELDLIST` macro in
   `plugins/flipperproto0/messages/*.pb.h` and checks each field (number, type, repeated, oneof) against the
   Rust schema. 144 fields in 67 messages match; the Rust schema is newer (protocol 0.25) and has more, never fewer.
2. **The bytes against the C++ app's encoder.** `tests/nanopb/driver.c` is built from the C++ app's own generated
   `.pb.c` files and nanopb (plain C, no Qt), fills each request exactly as the plugin's request classes do and each
   response as the firmware does, and prints the frames to `tests/fixtures/nanopb_frames.txt`. The Rust requests are
   byte-identical; the responses decode to the same values and re-encode to the same bytes. CI rebuilds the
   fixture from the C code and fails if it changes.
3. **A fake Flipper** (`crates/flipper-fake`): prints the banner and prompt, answers `start_rpc_session`, and
   serves read-only RPC from a scripted device, following the firmware's code (8 entries per list frame, `/` lists
   `any`/`int`/`ext`, non-ASCII names left out, property streams end with an empty frame, errors carry empty
   content). It records every byte the client sends, and it can misbehave on purpose: no prompt, silence, a garbage
   frame, an oversized frame, an error status, a flood of frames for other ids, a wrong response type, a cut-off
   frame. The CLI tests run the real `argus-cli` binary against it over a Unix socket and compare stdout (one JSON
   object), stderr, the exit status and the bytes on the wire, which must equal the C++ encoder's frames.
4. **Property tests and fuzz targets for every decoder.** The frame decoder has proptests (any bytes cut anywhere
   never panic and never buffer past the limit; messages round-trip however the stream is split; junk after valid
   frames does not lose them) and a cargo-fuzz target (`argus-tools/fuzz`, `rpc_frames`). Each new decoder gets the
   same: file listings and reads (phase 2), update manifests and `directory.json` (phase 7), DfuSe files (phase 6),
   tar backups (phase 2).

**The capture metadata against the C++ parser itself.** What a capture says about itself is stored as its
`meta` JSON and handed out by the Sarina API, so it must match byte for byte. `crates/argus-capture/tests/qt-oracle`
builds a small program from the C++ app's own `flipperfileformat.cpp` (QtCore only) that prints what
`recordCapture` would store; `tests/qt_oracle.rs` feeds it and the Rust port 3000 generated files per run (key/value
lines mixed with carriage returns, invalid UTF-8, BOMs, Unicode spaces, NULs, odd numbers, every suffix) and
requires identical output. The Linux workflow runs it; 13 seeds (39 000 files) agreed here. It found three Qt
rules the port now follows: the file is read in `Text` mode, which drops **every** `\r` byte, not only in `\r\n`;
each byte of an invalid UTF-8 sequence becomes its own U+FFFD; and `toInt` reads only up to a NUL and trims ASCII
whitespace (with `\v`) but no other kind.

**The C++ CLI against the same fake.** The C++ app finds a Flipper by USB VID/PID. A test-only hook
(`backend/testhooks.h`) changes that only when `ARGUS_TEST_SERIAL_PORT` names a port: the registry then does not
watch USB at all (a real Flipper plugged in is never seen), uses that port as the one device, does not raise DTR
(a pseudo-terminal has no modem lines) and does not fetch the firmware directory (no network). Unset, nothing
changes. The fake serves a pseudo-terminal (`flipper-fake --pty`), session after session as the C++ app reopens
the port. `argus-tools/crates/flipper-fake/compare-cli.sh` runs `qFlipper-cli backup` and `argus-cli backup`
against it and compares exit codes, the archives' files and bytes, and the requests each sent (decoded by the
fake, ids aside); it refuses a `qFlipper-cli` built without the hook. The Linux build workflow runs it after the
Qt build. Result on 2026-11-12: same files, same bytes, same storage requests in the same order. The C++ app
also probes the device first (protobuf version, `devinfo`, storage info, `/ext/Manifest`, reads and **sets the
clock**) and starts the screen stream and a status screen; the Rust CLI does none of that.

**Writes, restore and the factory reset against the C++ app.** The fake keeps its storage as clients change it
(`flipper-fake/src/storage.rs`) and applies the firmware's rules from `rpc_storage.c` and `storage_processing.c`:
`/int` is an alias of `/ext/.int` and always exists (`mkdir /int` is "already exists", removing it fails while it
holds anything), names for writes must be ASCII, a write opens its file with `CREATE_ALWAYS` on its first frame and
answers once after the last, another storage request in between answers the write "interrupted", removing what is
not there is OK, a folder that holds anything needs `recursive`, pings are answered, and a reboot or factory reset
ends the session without an answer (a factory reset empties `/int`). `--dump FILE` writes every folder and every
file's size and MD5 at the end, so two runs can be compared byte for byte. `compare-cli.sh` then has each app
restore its own backup and the other's onto a `/int` changed since the backup (one file rewritten, one removed, one
added), three more archives (the old format without end blocks and with stray zero blocks, GNU tar's record
padding, and a 150 KiB file that gets a status ping per chunk), a `/int` where the backup's folder is a file,
27 hostile archives and a gzip bomb, and the factory reset: both succeed or both fail, the same requests in the same order
and the same bytes on the fake, and for every hostile archive no change request at all (the Rust CLI does not even
open the port). The write requests are byte-identical to the C++ app's nanopb encoder (12 more frames in the
fixture: write chunks, an empty file, mkdir, delete with and without `recursive`, rename, ping, reboot, factory reset,
update). Result on 2026-11-12: 133 checks, all passed.

The C++ CLI's restore and `erase` wait for the device to come back over USB after its reboot, which a
pseudo-terminal cannot do; with the test hook set they take the request as done once it is sent (two more guarded
spots: `restartoperation.cpp`, `factoryresetutiloperation.cpp`).

**The Sarina control API against the C++ server.** The wire format is the contract, so it is proven three
ways. (1) `crates/argus-api/tests/qt_json.rs` feeds 4000 generated request lines per seed (numbers at
every edge, escapes, lone surrogates, invalid UTF-8, repeated keys, deep nesting, then cut, changed or
padded) to a program built from Qt's own JSON code (`tests/qt-oracle/json_oracle.cpp`) and to the Rust
`qjson`, and requires the same error text, the same compact and indented output, the same `toInt`/
`toString` reads and the same `id` echo: 20 000 lines over five seeds agreed, covering all twelve parse
errors. (2) `crates/argus-api/compare-api.sh` runs `qFlipper-cli chymaera serve` and `argus-cli chymaera
serve`, each with its own copy of the same files, an old-schema datastore and a capture library, sends
both the 71 recorded requests in `tests/fixtures/api_requests.txt` and compares the answers (times, port
and folders normalised), the datastore rows and events, the token file's life, the port argument,
`chymaera parse|import|selftest`, and both servers with the fake attached as their device: 43 checks. It runs in a private network namespace (`unshare -rn`)
whose only interface is its own loopback, so it can never reach the API I run; in a CI container without
user namespaces it uses that container's loopback. (3) The C++ answers are kept in
`tests/fixtures/api_responses.txt`; `tests/api.rs` replays the requests against the Rust bridge in
process, so every CI run of argus-tools checks them without Qt, and the Linux workflow checks the C++
server still gives exactly those answers. The pcap writer is compared the same way with the C++
`PcapExporter` (`tests/pcap.rs`: both formats, five link types, times before 1970, packets past the snap
length).

Differences from the C++ app found so far, all on purpose or harmless:

- **A corrupt stream stalls the C++ app.** It appends to its buffer until nanopb manages to decode, so a broken
  frame means waiting forever with a growing buffer. The Rust decoder tells "incomplete" from "invalid" and ends the
  session with an error; frames over 16 KiB are refused from their length prefix.
- **Empty strings.** nanopb sends a set-but-empty pointer string (`path: ""`), prost leaves it out; both decode the
  same. The Rust operations never send an empty path.
- **The C++ device-info flow sets the device's clock** on every connection. `argus-cli info` only reads.
- **`status.pb.c` is dead in the C++ app**: compiled, never used (the old `PB_Status` ping; ping is in `PB_System`).
  Not ported. Upstream's code, so I leave it there until the C++ goes.
- **Strings must be UTF-8 in Rust** (proto3 `string`); a frame with invalid UTF-8 fails to decode with an error,
  where the C++ app passes the bytes on. The firmware leaves non-ASCII names out of listings anyway.
- **Bytes glued to the `start_rpc_session` echo** are kept as RPC data; the C++ app would discard them and time out.
- **Control characters** (including DEL and the C1 range) in anything printed are escaped, so a file name on the
  device cannot drive the terminal.
- **The API's request buffer.** The C++ server refused a client once one read held over 1 MiB, even when it was
  many complete short requests; the Rust server answers the complete lines first and refuses only an unfinished
  line over 1 MiB. It also drops a client that leaves over 16 MiB of answers unread, and takes at most 1000
  clients at once (the C++ server had no limits there).
- **The runtime folder for the token** must be mine and 0700 (`$XDG_RUNTIME_DIR`, else `/run/user/UID`); the Rust
  server never falls back to a folder under `/tmp` as Qt can.
- **Kept on purpose, in both:** a lone UTF-16 surrogate in the `token` is dropped before the comparison (Qt's
  `toUtf8`; the token is still needed), and `capture.list` with a negative `limit` returns every row (SQLite's
  rule).
- **A device in `serve` and `watch`:** the Rust CLI opens only the port it is given and has no hot-plug: an unplugged
  device is detached and `watch` ends. Its idle worker asks the protobuf version once a second. The C++ app logs
  more about a device (status strings, RPC session changes) and, on connecting, sets the clock and starts the screen
  stream; the Rust side logs attach, offline and detach only. The Rust selftest checks the Rust pieces in process;
  the archive and name checks of the C++ selftest are flipper-rpc's tests.

Found in the C++ app by running it against the fake, and **fixed in both versions** on 2026-11-12 (a bug the
port finds is fixed in the C++ too). `compare-cli.sh` has a case for each, and both apps now agree on all of them:

- **A missing `data` field crashed it.** `storageresponse.cpp`, `guiresponse.cpp` and `statusresponse.cpp`
  dereferenced nanopb's `data` pointer unchecked; a device that leaves an empty `bytes` field out (valid proto3;
  the firmware never does) made the app segfault. Now a missing field is empty. Cases: `omit-empty-data`,
  `frame-without-data`.
- **Screen frames of the wrong length** were drawn anyway: the canvas reads 1024 bytes for the 128x64 screen, so a
  shorter frame read past the end. The streamer now drops any frame that is not exactly 1024 bytes. (The Rust port
  must do the same when it gets the screen streamer, phase 3.)
- **A short or long read went unnoticed.** `StorageReadOperation` now fails when the bytes received differ from the
  stat, which covers backup, directory download, capture pull and snapshots. The backup exits non-zero and leaves
  no archive. Cases: `short-read`, `long-read`.
- **Its backups confused standard tar, and its restore lost files from them.** The writer added a zero block after
  any 512-aligned file (GNU tar stopped there), truncated names over 99 bytes and wrote no end blocks; it now pads
  correctly, refuses long names and ends with two zero blocks. The reader ended at the second zero block anywhere
  in the archive, so an old archive with two 512-aligned files lost everything after the second; it now ends only at
  two zero blocks in a row, so old and new archives both restore whole (`chymaera selftest` checks both).
- **No name checks in backup and directory download, and a delete.** `GetFileTreeOperation` now leaves out (and
  lists as refused) any name that is empty, `.`, `..`, not UTF-8, over 255 bytes, or holds `/`, `\`, NUL or a
  control character, the same rule as the Rust `safe_name`; nothing under such a name is read. The directory
  download refuses an existing local folder instead of deleting it. Case: `hostile`.
- **An empty tree hung backup and directory download** (they waited for a last file that never came); they now go on.

Found while porting the control API, and **fixed in both versions** on 2026-11-12. `compare-api.sh` has a case for
each:

- **A second server replaced the running one's token.** Started without a token, the server wrote a new token
  file *before* taking the port, so starting `chymaera serve` while the GUI's server held 44700 overwrote the
  token file and then failed: Sarina's clients could no longer reach the running server. The port is now taken
  first.
- **Ctrl+C left the token file behind.** `serve` died on the signal; it now stops cleanly and removes the file.
- **`capture.import` read any local path.** A FIFO hung the app (forever, the API with it), `/dev/zero` never
  ended, a folder was recorded as a capture, and because the generic parser stores every `Key: Value` line, a
  caller holding only the token could read other files of mine through `capture.list`. Only regular files are
  read now (also by `chymaera parse`), a file over 64 MiB is kept unparsed, and over the API only capture
  files (`.nfc .sub .rfid .ir .ibtn .pcap .pcapng`) are taken.
- **NULL was sent as `""`.** `capture.list` gave `session_id`, `sha256` and `local_path` as empty strings where
  docs/SARINA_API.md says null (Qt's SQLite driver hands NULL out as a null string). Now null.
- **`serve`'s port argument** wrapped (70000 became 4464) and a non-number silently meant 44700. Both are now
  refused.
- **"no token"** was logged and printed while a token was required (the one written to the file). It now says
  where the token was written.
- **A file of millions of tiny lines took gigabytes.** Both readers made one string pair per line of a file up to
  64 MiB (about 21 million `a:` lines), on any capture pulled off a card. A file with more than 200 000 lines is
  now kept unparsed by both (`FlipperFileFormat::MaxLines`, `flipperfile::MAX_LINES`); the Qt oracle test has the
  cases at the limit.

Found while porting the restore (phase 4), and **fixed in both versions** on 2026-11-12. `compare-cli.sh` has a case
for each:

- **The restore could not work on current firmware.** It removed every path in the backup without `recursive`,
  `/int` itself first, which the firmware refuses while `/int` holds anything ("directory is not empty"); and it then
  made `/int`, which is always "already exists" now that `/int` is an alias of `/ext/.int`. Any top-level folder of
  the archive was removed and written on the device, not only `int/` (an archive with `ext/` in it reached the SD
  card). Now both apps check the whole archive first, list `/int`, refuse a backup whose file is a folder on the
  device (or the other way round) before writing anything, make the missing folders and write every file. Files on
  the device that are not in the backup stay, as before. Cases: `restore-*`, `good-*`, `conflict`, `hostile-outside-int`.
- **Unpacking wrote outside its folder.** The C++ restore unpacked the archive to a temporary folder before
  looking at it, and the tar reader took any name: folder entries named `..` (`int/../`, `int/../../`) made
  `int/../../escaped.txt` land two levels above the folder. The temporary folder was named after the device
  (`hardware.name`, which the device controls), as was the backup's. The C++ restore no longer unpacks anything (it
  writes from the archive in memory), and the reader (`TarArchive`, also used for firmware update packages) now
  refuses an unsafe name, a link, a missing checksum match, a name with no NUL in its 100 bytes, a ustar prefix, a
  size that is not octal (it read past the field with `strtol`, and a base-256 size as 0), a folder with data,
  a name twice, an entry before its folder (such files used to be dropped silently) and cut data. Cases:
  `hostile-*`, and a check that no `escaped.txt` exists anywhere.
- **A cut gzip file was taken as complete,** and there was no limit to what it unpacked to. `GZipUncompressor` now
  requires the end of the gzip stream (zlib checks its CRC and length there) and stops at 1 GiB, a restore at 80 MiB
  of tar, 64 MiB of files, 16 MiB per file and 10 000 entries (the Rust reader has the same limits). Cases:
  `hostile-truncated-gzip`, `bomb`, `hostile-huge-file`.
- **A restore replaced (and then deleted) a file next to the backup.** `TarZipArchive` unpacked `name.tgz` to
  `name.tar` in the same folder (`baseName()`, so `my.backup.tgz` became `my.tar`) and removed it afterwards; it
  now uses the app's temporary folder. A gzip error left it with no index, which `TarZipUncompressor` then used
  (a null pointer); it now stops.

A regression of my own, caught by porting the capture sync: once `GetFileTreeOperation` left unsafe names out,
the C++ capture pull stopped counting them as failed (as `stagedPath` used to). `CaptureSync` now counts every
refused name as failed again, and the Rust pull does the same.

What still differs, on purpose: the C++ app probes the device before a backup (and **sets its clock**) and starts the
screen stream and a status screen; the Rust CLI only reads what the command needs. For writes: the Rust CLI asks for
`--yes` (the C++ CLI is upstream's and writes when told to; the GUI asks in its dialogs), checks a backup before it
opens the port (the C++ app connects first), refuses non-ASCII names before sending them (the firmware refuses them),
sends a large file up to each status ping and waits for that ping's answer (the C++ app sends it all at once; the
frames are the same), and after a reboot or reset waits for the device to leave instead of for it to come back
(it has no USB hot-plug). The C++ CLI exits 255 on any error, the Rust CLI 1. For capture pull: the Rust CLI refuses a path
outside the capture folders before it opens the port (the C++ CLI refuses once the device is ready), names the
staging folder in UTC (the C++ app in local time), creates it 0700 and its files 0600, removes a file whose read
failed, and does not read `devinfo` or start the screen.
